# ADR-0016: A shared demo password for changes on the live site

- **Status:** Accepted
- **Date:** 2026-10-18
- **Requirements:** M7 AC-8 (answer to M7 Q2); PRD non-goal "auth beyond a single seeded user"

## Context
The live link is public. Reconcile has one built-in user and no logins (the PRD keeps real
authentication out of scope), so anyone with the link could upload files, decide problems, or
correct fields.

## Options
1. **Browser password prompt (HTTP basic auth) on the whole site:** simple / visitors can't even look
   without the password, and the browser's prompt looks broken in a polished app.
2. **Basic auth only on write requests at the web server:** reading stays open / the browser's
   native prompt appears unpredictably for background requests.
3. **A demo password checked by the API for changes, with an "Unlock changes" dialog in the
   website:** reading stays open, the experience matches the rest of the site, and it's off locally.

## Decision
Option 3. When `DEMO_PASSWORD` is set, the API refuses `POST` requests that change data unless the
request carries a valid signed, HTTP-only cookie, which `POST /demo/unlock` sets after checking the
password (compared in constant time, with a small delay after a wrong try). The website shows an
**Unlock changes** button and opens the dialog when a change is refused. It is a gate for a demo,
not user accounts: everyone who unlocks acts as the one built-in user.

## Consequences
- ➕ Visitors can explore everything; people you give the password to can try the full flow.
- ➕ No change to local development or the browser test (the variable isn't set there).
- ➖ One shared password: no per-person history. Acceptable while the PRD keeps auth out of scope.
- ➖ The cookie-signing key and password are more secrets to manage (generated by Terraform).
